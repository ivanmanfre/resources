AI Orientation Session — Call Guide

$500 · 90 minutes. Follow this top to bottom. The goal: get Derek set up to run Claude Code himself, and pick one real thing to build.

How to use this: You direct, Derek drives — he types, you talk him through it. He almost never runs a command himself; he tells Claude what he wants in plain English and Claude does it.
Green box = what Derek says to Claude Dark box = a command to type once Red box = say this out loud (a gotcha)
1

Open the call

~10 min

Set the frame: "We'll set up your tools, then pick one real thing to build. You drive, I steer. After this you get a written plan." Make sure you're on Zoom (so you can grab his screen if needed).

Then ask the two questions that decide everything:

  1. "Is the data you'd automate something you can't send to a cloud like Claude?" → decides what runs on his Mac vs in the cloud.
  2. "What's the one job eating the most of your week?" → that's the first thing you build.
2

Install the tools

~15 min

Step 1 — VS Code + Claude Code

  • Download VS Code from code.visualstudio.com and install it.
  • Inside VS Code, install the Claude Code extension and sign in.
Check first: Claude Code needs a Claude Pro or Max plan to run. If he doesn't have one, set it up now or it'll eat your call time. Max is better for his ambitions; Pro gets him through today.

Step 2 — Sign into GitHub (the one manual thing)

This is the only step Claude can't do for him. In the VS Code terminal:

gh auth login

It opens a browser, he clicks approve, done. (If GitHub CLI isn't installed, he can just say it — see below — and Claude installs it.)

Install the GitHub CLI and log me in.
3

Set up his project + repo

~15 min

Open his project folder in VS Code. From here on, he talks to Claude in plain English. First, turn the folder into a synced, private repo:

Turn this folder into a git repo, add a .gitignore that keeps my .env and API keys out, and push it to a new private GitHub repo called [name].

Claude does all the git work. Then give it a memory of his setup:

Write a CLAUDE.md for this project — my tools, how I work day to day, and the rules ("never do X"). Keep it short.

Read it together and fix anything wrong. This file is the single most valuable thing — Claude reads it every session, so he never re-explains his setup.

4

Permissions (so Claude stops asking)

~10 min

By default Claude asks before every command. For a beginner that's exhausting. Fix it:

  • Type /permissions to see and edit what Claude is allowed to do on its own.
  • Allowlist his routine-safe commands so it stops asking — his git, ollama, etc.
  • Modes (press Shift+Tab to cycle): default (asks each time) → accept-edits (auto-approves file edits once he trusts it). Start on default; move to accept-edits after a couple sessions.
Never turn on "bypass permissions." That lets Claude run anything with no check — dangerous on a real machine.

A starter .claude/settings.json he can paste in (Claude can write it for him too):

{ "permissions": { "allow": [ "Bash(git commit *)", "Bash(git push *)", "Bash(ollama *)" ] }, "model": "claude-opus-4-8" }
5

Memory (it's automatic)

~5 min

Good news — there's nothing to build. Claude Code remembers his project on its own (on by default in recent versions). Type /memory to see it.

  • Durable facts and rules → put them in CLAUDE.md (from Part 3).
  • The rest → Claude saves automatically as he works.
Say this: "You do NOT need a database or a 'memory system' yet. The built-in memory covers you until you're way bigger. Skip it." Telling him what not to build is half the value.
6

Skills + commands

~15 min
Clear up the #1 confusion: you do not install a skill by telling Claude "install stochastic audit." That does nothing. Skills come from the /plugin menu, or they're just files in a folder.

Install Superpowers (a great free pack)

Type /plugin → it opens a menu. Add the official marketplace and install it. Or type it directly:

/plugin marketplace add anthropics/claude-plugins-official /plugin install superpowers@claude-plugins-official

It adds disciplined workflows (planning, debugging, double-checking work). Worth it on day one.

Add the starter commands (yours, made generic)

The 4 stochastic commands are just files. Drop them into his repo at .claude/commands/ and they become /stochastic-decision, /stochastic-research, /stochastic-audit, /stochastic-red-team. Since they're in the repo, they sync to both his machines.

Copy these four files into .claude/commands/ in this project.

The commands he'll use every day

  • /init — first time in a project: builds the CLAUDE.md for him.
  • Plan mode (Shift+Tab to "plan") — "make a plan before you build." He reviews it, then says go. Safest habit.
  • /clear — start fresh when he switches to a different task.
  • /compact — shrink a long chat without losing the thread.
7

Connect his tools

~10 min

GitHub — already done

The gh auth login from Part 2 is all he needs. Claude uses it for everything GitHub. (There's also a GitHub MCP server and personal access tokens, but the CLI is the simple path — don't overcomplicate it for him.)

His other tools — MCP

MCP is how Claude connects to outside tools (his CRM, docs, calendar). Add only the 1–2 that matter; skip the rest.

Add the [tool] MCP server so you can read my [CRM / docs / calendar].
8

The local model

~10 min

Only if Part 1 flagged private data. Running a model on his Mac is simpler than it sounds: install one app, download one model.

  1. Install Ollama from ollama.com (or say "install Ollama" and Claude does it).
  2. Pull a model: ollama pull llama3.1:8b (or have Claude do it). 8B fits most Macs; the Mac Studio can run a bigger one.
  3. It now runs at localhost:11434 — that's the address n8n points to for private parsing.
Plain terms: Ollama is the engine; the model (Llama, Qwen…) is what it runs. You install the engine, then download a model into it.
Do a 10-min dry run before the call — install Ollama, pull an 8B model, chat with it once. Then you'll never be lost explaining it.
9

Both machines (office Mac + home PC)

~5 min

He doesn't choose a machine — the repo lives on both. Install the tools on each, sign into GitHub on each, then it's all plain English:

Clone my private repo [name] and set it up here.
Pull my latest from GitHub.
Say these out loud: secrets never go to GitHub (they're git-ignored) · the local model stays on the Mac · his memory is per-machine, but CLAUDE.md syncs.
10

Build one real thing

~20 min

This is the part he remembers. Pick one (the rest is his backlog):

  • Inspection-report parser — raw field notes/PDFs → clean compliance fields. (Best private + bulk payoff; runs on the local model.)
  • Hottest untouched leads — score his leads, show the ones not yet contacted. (Fastest money win; runs on Claude.)

Sketch it together: what kicks it off → the steps → where Claude, n8n, and the local model each fit → what could break. Then he builds it WITH Claude in plain English.

★ The habit that matters most: make Claude prove it works. He can't read the code, so he says — "write a test, run it, and show me it passed." That's how a non-dev trusts the output.
11

Optional: a live dashboard if he's hungry

bonus

If the first build lands and there's time/appetite, the wow-moment is a simple web page that's always on. Keep it to one useful number, e.g. "sites needing an inspection this week" or "which automations ran / failed today."

Build a simple one-page web dashboard that shows [the one number], and deploy it to Railway so it's always online at a link.

Claude builds it and walks him through deploying to Railway (free to start). Now he has a live URL he can check from his phone. Don't over-scope it — one number, one page.

12

The 5 habits + 3 traps

Drill these 5 habits

  1. CLAUDE.md first — keep it short and current.
  2. Ask for a plan before building — review, then go.
  3. Point at files — say @filename instead of describing it.
  4. Make it verify — "test it and show me it works."
  5. Commit often — checkpoints he can roll back to.

Warn him off these 3 traps

  • Kitchen-sink chat (ten unrelated tasks in one session → Claude loses the thread). Fix: /clear between tasks.
  • Bloated CLAUDE.md (pasting whole docs → rules get buried). Fix: keep it tight, prune often.
  • Trusting without checking. Fix: always make it test/show.
13

Leave alone + close

Tell him what NOT to build (yet)

  • No database / "memory brain" — the built-in memory is enough.
  • Don't force everything onto the local model — let Claude do the thinking.
  • Don't build all the skills at once — one working thing beats ten half-built ones.

His next steps this week

  • VS Code + Claude Code + his CLAUDE.md.
  • Ollama + a model on the Mac (if private data).
  • Finish the one build you started.
  • Watch for the written plan you'll send.
